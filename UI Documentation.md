## **UI Documentation — Dcreators** 

## **Tagline:** _Hire Creatives. Buy Art. Build Ideas._ 

## **1. Introduction** 

## **1.1 Purpose of the Product** 

**Dcreators** is a multi-sided creative ecosystem designed to connect **clients, creative consultants, artists, photographers, designers, and artisans** on a single digital platform. The application enables users to: 

- **Hire creative professionals** for project-based work 

- **Assign and manage creative projects** 

- **Browse and purchase artworks/craftworks** 

- **Showcase creator portfolios** 

- **Handle payments, work orders, and reviews** 

- **Track project milestones, sales, and deliveries** 

## The platform combines **creative marketplace functionality** with **project management workflows** , 

positioning itself as a unified environment for both **creative service procurement** and **art commerce** . 

## **1.2 Documentation Objective** 

This UI documentation is intended to: 

- explain the structure and functionality of the Dcreators interface, 

- document the user flow and screen behavior, 

- define reusable UI components and visual patterns, 

- support developer handoff and future design iteration, 

- establish a consistent reference for usability, interaction, and implementation. 

## **1.3 Product Scope** 

The prototype indicates three major platform pillars: 

1. **Hire Creatives** – assign projects to consultants/creatives and manage deliverables 

2. **Buy Art** – discover, purchase, and track artworks or handcrafted products 

3. **Build Ideas** – collaborate, negotiate, review, and complete creative projects end-to-end

## **3. User Flow** 

The Dcreators platform contains multiple user journeys. Based on the prototype, the key flows are: 

## **3.1 Flow A — Creator Onboarding & Profile Setup** 

**Landing Page → Create Account → Creator Account → Portfolio Update → Consultancy Services → Creator Dashboard** 

## **Steps:** 

1. User lands on the **Welcome / Home screen** . 

2. Selects **Sign Up** . 

3. Completes **Create Your Account** form with profile image, name, email, mobile, address, and sign-in method. 

4. Proceeds to **Creator’s Account** and submits professional details, identity details, banking details, and consultancy terms. 

5. Uploads **portfolio artworks** and fills artwork metadata such as title, size, medium, price, and availability. 

6. Updates **consultancy services** and fees. 

7. Enters the **Creator Dashboard** / professional ecosystem. 

**This flow establishes the creator as a verified consultant or seller on the platform.** 

## **3.2 Flow B — Client Hires a Creative Consultant** 

**Explore Creatives → Hire & Assign Project → Assignment Status → Select Consultant → Payment → Work Order → Project Dashboard** 

## **Steps:** 

1. Client explores available creative consultants by category. 

2. Client opens **Hire & Assign Project** form. 

3. Client enters: 

   - creative role 

   - selected service/item 

   - assignment date 

   - assignment budget 

   - assignment brief 

4. Client submits assignment or saves draft. 

5. Platform shows **Assignment Status** with candidate consultants near the budget range. 

6. Client selects a consultant and proceeds to **Pay Advance** . 

7. Payment confirmation is generated. 

8. A formal **Work Order** is created. 

9. Client accesses **Project Dashboard** for review cycles, feedback, revisions, approval, and final payment. 

## **This is the core service procurement flow.** 

## **3.3 Flow C — Consultant Handles Assigned Project** 

## **Project Dashboard → Review Assignment → Negotiate / Collaborate → Upload Designs → Receive Feedback → Final Approval → Final Payment** 

**Steps:** 

1. Consultant receives incoming project request in the **Project Dashboard** . 

2. Consultant can: 

   - accept project terms, 

   - negotiate budget and deadline, 

   - seek collaboration with another consultant if needed. 

3. Consultant uploads first design review files. 

4. Client provides feedback. 

5. Consultant uploads revised design for second review. 

6. Final files are submitted for approval. 

7. Final payment is released. 

8. Final artwork/design files become downloadable. 

## **This flow is visible in the project assignment and review screens.** 

## **3.4 Flow D — Buyer Purchases Artwork** 

**Marketplace / Sales Dashboard → Artwork Detail / Request → Payment → Confirmation → Delivery Tracking** 

**Steps:** 

1. Buyer browses artwork listings in the marketplace. 

2. Buyer selects a product/artwork and proceeds to purchase. 

3. Payment screen shows order summary and payment method. 

4. Buyer completes payment. 

5. Payment confirmation screen is displayed. 

6. Artwork processing / courier status is updated. 

7. Buyer may rate the experience. 

**This flow is visible across the Buy Art and payment screens.** 

## **3.5 Flow E — Creator Artwork Sales Management** 

**Sales Dashboard → Request for Purchase → Accept / Pass / Decline → Dispatch / Courier Update → Payment Release** 

## **Steps:** 

1. Creator receives purchase request in **Sales Dashboard** . 

2. Creator reviews: 

   - artwork details 

   - buyer address 

   - payment status 

   - buyer information 

3. Creator accepts or declines the request. 

4. After acceptance, dispatch and courier details are added. 

5. Payment is released upon delivery or transaction completion. 

**This establishes the seller-side commerce workflow.**

## **7. Interaction Behaviour** 

This section explains how the interface behaves across common user actions. 

## **7.1 Form Submission Behavior** 

Forms such as **Create Account** , **Creator Account** , and **Hire & Assign Project** should support: 

- required field validation 

- inline error states 

- success confirmation 

- save draft where applicable 

- upload completion feedback 

## **7.2 File Upload Behavior** 

All upload interfaces should support: 

- drag-and-drop upload 

- tap/click upload 

- file size validation 

- file type validation (JPG, PNG, PDF, ZIP, etc.) 

- progress or upload success state 

- replace / delete file action 

## **7.3 Payment Behavior** 

Payment screens should: 

- confirm selected payment method 

- validate card input 

- display transaction summary before payment 

- redirect to confirmation on success 

- preserve transaction reference and order/project linkage 

## **7.4 Project Review Cycle Behavior** 

For project-based assignments: 

1. consultant uploads review file 

2. client views submission 

3. client enters comments/feedback 

4. consultant uploads revision 

5. client approves final output 

6. balance payment is released 

7. final deliverables are downloadable 

**This is one of the most important workflow behaviors in the app and should be clearly supported with status markers and notifications.** 

## **7.5 Sales Request Behavior** 

For creator-side sales: 

- incoming request should display artwork, buyer, address, and payment status 

- creator should be able to accept, decline, or pass the request 

- once accepted, dispatch and courier information should be stored 

- delivery confirmation should trigger payout or final closure. 

## **7.6 Collaboration Behavior** 

In project collaboration mode, a creator can browse other consultants and invite them to collaborate. Expected behaviors: 

- candidate list with consultant summary 

- “Collaborate Now” CTA 

- collaboration request sent state 

- received response / pending state 

## **7.7 Dashboard Behavior** 

Dashboard views should support: 

- filtering or switching between projects/sales/history 

- progress tracking 

- quick actions for upload, review, or navigation 

- calendar/project planning interactions 

- summary cards for metrics and recent updates 

## **7.8 Review & Rating Behavior** 

After order/project completion: 

- user can rate service 

- enter qualitative feedback 

- apply quick tags 

- submit review to creator profile 

This helps strengthen trust signals and consultant reputation.
